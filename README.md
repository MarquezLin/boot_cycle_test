# GVFG 冷／暖開機 audio 循環測試（2026-10-14）

推薦入口：`boot_cycle_test/bin/GVFG_BootCycleTest.exe`（2026-10-14）。
日常只需雙擊 **bin/GVFG_BootCycleTest.exe**。UI 與背景檢查已合併到同一個 EXE。
開啟視窗不會開始測試，請先選擇待測 EXE 與模式，再按試跑或正式測試。

## 腳本迴圈

在流程編輯器選取步驟後，按「在後補充…」，勾選「跳回前面的步驟」，選擇目標和次數後插入。加入後可雙擊迴圈步驟修改。也可在 JSON 的 `steps` 陣列加入下列步驟。若放在第 5 步，會從第 2 步重跑到第 5 步，跳滿 3 次後執行第 6 步。

```json
{"type": "loop", "targetStep": 2, "jumpCount": 3}
```

`targetStep` 是從 1 開始的步驟編號，須指向前面的步驟。調整步驟順序後，請確認目標編號。`jumpCount` 是實際跳轉次數，填 0 就直接執行下一步。每次執行完整流程時，各跳轉步驟的計數會重新開始。單步試跑會檢查跳轉設定。

步驟失敗時，本輪腳本立即停止。若在跳轉回來後失敗，工程檢視與日誌會顯示失敗步驟及跳轉次數。預設會一併停止正式開機循環。

## 操作

- 左上選擇冷開機或暖重開機，設定自動保存到 test_settings.ini。
- 待測 APP 由匯入 JSON 的 executable 指定。若 JSON 或 EXE 路徑失效，測試會停止於環境檢查。
- 試跑：檢查 audio，顯示 PASS／FAIL、接收 frame 數與本次紀錄；不關機、不重開機、不呼叫 UART。
- 正式測試：登入後等待 20 秒再啟動 APP，PASS 後等待 15 秒，執行所選模式的電源動作。
- 停止：建立 STOP，阻止尚未執行的控制動作。手動重新開始會清除 STOP／FAILED。
- 關閉測試中的視窗也會要求停止，等測試結束後再關閉即可。
- 開啟紀錄資料夾：查看歷史 CSV 與 log；視窗會載入近期歷史紀錄並追加本次進度。
- 測試執行中不能切換模式。再次開啟程式只會顯示已開啟的視窗。

## 在 UI 管理自動啟動

視窗直接顯示自動啟動的安裝狀態，每秒更新。

- 解除自動啟動：移除本工具的捷徑與先前 CMD 啟動檔，不刪除程式、模式設定或紀錄，也不建立 STOP。
- 已安裝／未安裝：顯示啟動項目是否存在及是否指向目前 EXE、帶有 --auto-run。

## 判定與紀錄

Windows UI Automation 啟動 Customer Sample 的 Start，讀取 CH0 Audio 的 received=N frames。
30 秒內 N > 0 即 PASS；不檢查聲音振幅、播放或持續接收。
失敗會建立 FAILED，保留 APP 與電腦現場，不關機或重開機。

兩種模式共用 boot_cycle_results.csv 與 boot_cycle_detail.log，PASS detail 及每輪起始 log 記錄 Mode=cold／warm。
PASS 表示該輪 JSON 流程的檢查通過。

待測 APP 由 JSON 指定。CH0 audio 範本使用 Customer Sample 的 CH0 Start AutomationId 及音訊計數文字。

## 冷開機外部控制器

requestExternalPowerCycle() 尚未傳送 UART 指令，會記錄 CONTROLLER_NOT_CONFIGURED。
因此目前冷開機 PASS 後只會關機，需要外部恢復供電，完整自動循環尚未接通。

未來需確認 COM port、baud rate、封包、ACK、取消機制及電源切換時序。
控制器必須獨立供電，自行完成延遲斷電 → 保持斷電 → 恢復供電。
斷電保持 20 秒從實際斷電起算，是否足夠放電需硬體驗證。
只有整個序列獲確認才回傳 Armed；傳送／ACK 失敗回傳 Failed，阻止關機。
關機延遲需容納實際 Windows 關機時間；APP 阻擋關機時，固定時間切電仍可能變成運作中斷電。
STOP 目前不能撤回控制器已接受的序列，UART 整合時需另外實作取消協定。
BIOS 需設定恢復供電後自動開機。

## 發布給其他使用者

修改程式後，直接雙擊專案根目錄的 `package_release.bat`。它會載入 Visual Studio x64 編譯環境，在獨立的 `build/package-release` 目錄設定並建置最新 Release，再收集 Qt、VC++ 安裝程式、OCR 引擎／DLL／語言資料及授權，輸出 ZIP 到 `release`。不需要先在 Qt Creator 手動建置。

顯示 `SUCCESS` 才表示本次完成；失敗時會顯示錯誤並暫停，完整紀錄位於 `build/package_release.log`。ZIP 的版號取自 `CMakeLists.txt` 的 `project(... VERSION ...)`；同版號重新打包會覆蓋該 ZIP，不同版號會保留舊包。不要在打包時修改原始碼。

此批次檔供開發電腦使用，收件者只需收到 ZIP。預設使用 `C:/Qt/6.10.2/msvc2022_64`，並以 vswhere 尋找 Visual Studio C++ Build Tools。工具位置變更時，可修改批次檔上方的預設路徑，或設定 `QT_ROOT`、`CMAKE_EXE`、`NINJA_EXE`、`VS_ROOT` 環境變數。請保留 `third_party/ocr` 及 `distribution/licenses`；搬移原始碼到另一台開發電腦時也要帶上這些發布資源。命令列自動化可使用 `package_release.bat /nopause`，成功回傳 0，失敗回傳非 0。

使用 Release Kit 建置。CMake 提供 install 與 package 目標，透過 Qt 部署流程收集 EXE、Qt DLL、plugins 及 VC runtime 部署檔案；ZIP 僅包含安裝規則列出的檔案，排除個人設定、STOP、FAILED、CSV、log、history 與原始碼。

在 Qt Creator 可新增 CMake 建置步驟，目標選擇 package；或在已配置 MSVC 環境的終端執行（將 <Release建置目錄> 換成實際位置）：

```text
cmake --build <Release建置目錄> --target package
```

ZIP 產生於該建置目錄，檔名中的版本取自 CMakeLists.txt。打包前請保留 third_party/ocr 的完整引擎、相依 DLL、tessdata 及 distribution/licenses；缺少引擎時 package 目標會直接失敗，避免產生缺件套件。
如果只要部署資料夾，可使用：

```text
cmake --install <Release建置目錄> --config Release --prefix <新的部署資料夾>
```

部署目錄應使用新的空資料夾，避免保留舊檔。不要使用 Debug 版當作對外發布版。

收件者操作：

1. 解壓縮整包到可寫入的位置，保留 bin 與 plugins 等完整結構。
2. 若包內含 VC runtime 安裝程式，依目標電腦環境安裝。待測 APP、對應驅動與硬體另行準備。
3. 開啟 bin/GVFG_BootCycleTest.exe，按「瀏覽…」選擇待測 APP，選擇模式，先試跑。
4. 確認結果後按「安裝自動啟動」，下次登入會使用目前工具位置及該資料夾保存的設定。
5. 若搬移工具，從新位置開啟後按「更新自動啟動」。搬移時一併保留設定與 Qt runtime 檔案。

試跑、正式測試與安裝自動啟動前，都會確認待測 EXE 與設定／紀錄寫入能力。檢查失敗會在狀態及本次紀錄區顯示原因，不啟動測試或執行電源動作。這是檔案與寫入檢查，不能取代待測 APP 的驅動、UIA 或硬體試跑。
## 紀錄與累計次數

畫面顯示累計次數，區分正式測試與試跑，並列出 PASS、FAIL、停止與未完成數量。每次啟動工具會從 boot_cycle_detail.log 重建統計，因此重開機後保留；開始後尚未出現結果的輪次列為未完成。STOP／FAILED 導致跳過或環境檢查未通過時，不算一次測試。

同一輪先 audio PASS、再發生電源控制 FAIL 時，統計改列 FAIL，不重複計次；audio PASS 後手動停止電源動作仍保留 PASS。PASS 不代表已完成實際電源循環。累計包含所有已保存的模式與待測 APP 紀錄，更換 APP 不會自動歸零。

紀錄區顯示最近最多 3000 行（載入時最多讀取最後 512 KiB 文字），完整 log／CSV 可從「開啟紀錄資料夾」查看。累計統計使用完整 log，不受畫面行數限制。

測試結束或停止後，可從主畫面按「匯出完整報告」。HTML、CSV、詳細紀錄和逐輪證據會放在 EXE 旁的 `reports/trial` 或 `reports/formal`，再依 `cold`／`warm` 分類。正式測試重開機續跑後會合併於同一批報告。

「清除本次暫存」只刪除最近一批尚可匯出的暫存，保留累計紀錄與已匯出的報告。測試執行中不可清除或匯出。
## 通用測試流程

在「通用測試流程…」編輯流程並按「保存」。回主畫面按「匯入流程…」，選擇已保存的 JSON。試跑、正式測試及登入後自動測試都直接讀取所選檔案。

1. 選擇待測 EXE、啟動參數與工作目錄（工作目錄留空時使用 EXE 所在資料夾）。
2. 新增、刪除、上移／下移步驟，在下方設定所選步驟。
3. 先執行「啟動 APP」及「等待視窗」，再設定操作與讀取。
4. UIA 控制項可按「取控制項」，在倒數 3 秒內把滑鼠停到待測控制項上；名稱採完全符合，也可填 regex: 加正規式。名稱與 AutomationId 皆填時須同時符合；多個符合項會拒絕操作。
5. 位置點擊與 OCR 可按「擷取並框選」，在截圖上拖曳；位置點擊使用框中心，OCR 使用整個框。座標相對於視窗內容區，以實體像素保存。改變 APP 布局、視窗尺寸或 DPI 時需重新框選並試跑。
6. 選擇步驟按「單步試跑」，確認結果與原始值，再執行完整流程。
7. 按「保存流程」保存 JSON；下次開啟編輯器會嘗試載入上次保存的流程。欄位的「自動套用」只更新目前編輯內容，不等於已寫入 JSON。

支援啟動 APP、等待主視窗、UIA Invoke 點擊、視窗位置點擊、Unicode 文字輸入、Enter／Tab／Esc／Ctrl+A／Ctrl+C／Ctrl+V／Alt+F4、等待時間、UIA 文字讀取、OCR、讀取值判定。

讀取步驟的預期值留空時只讀取；填入預期值會在逾時前輪詢等待符合條件。字串可相等／包含／正規式符合；數字可比較或填「最小值,最大值」範圍。數字判定取第一個數字；若文字有多個數字，請在讀取步驟的「擷取正規式」填入含括號群組的正規式，例如 received=([0-9]+)，取出 received 的數值。無法解析不會當作零。

「判定讀取值」使用同一流程最近一次成功讀取的值；單步試跑可沿用最近一次讀取值。完整流程會重新開始讀取狀態。編輯讀取來源後，請重新執行讀取步驟。

發布套件內附完整 Tesseract runtime，預設自動選用 bin/ocr/tesseract.exe。舊流程保存的引擎路徑若不存在，會重新尋找套件內引擎。語言可填 eng、chi_tra 或 eng+chi_tra，須保留對應 traineddata；使用其他語言時需自行補上語言檔。

每次流程試跑／完整執行在 EXE 旁的 flow_results 建立獨立目錄，保存實際流程 JSON、flow.log、result.txt、OCR 區域 PNG；步驟失敗時也會嘗試保存 failure.png。主畫面「開啟紀錄資料夾」可找到這些目錄；「清除紀錄」只清除原本開機測試 CSV／log，不刪除 flow_results。

截圖從桌面顯示內容依待測視窗客戶區擷取，保留原始像素，以支援 GPU 預覽。截圖前會將超出螢幕的待測視窗移回目前螢幕可用範圍，僅移動位置而不主動縮放，以保留框選座標；視窗本身大於可用範圍時會提示縮小後重新框選。視窗必須可帶到前景；偵測到取樣點被其他視窗遮擋時會提示，請移開遮擋，桌面鎖定時無法正常擷取。多個同 APP 視窗可在各步驟的「此步驟待測視窗」選單指定，選擇會隨流程保存；同名視窗無法唯一識別時會拒絕操作。啟動器另外產生子程序的 APP 尚未支援自動追蹤。UIA 原生呼叫的執行時間受待測 APP 的 provider 影響，停止會在該呼叫返回後生效。

## 可選測試範例

流程編輯器有範例下拉清單，可選文字來源 UIA／OCR，以及「追加檢查步驟」或「取代流程（含啟動／等待）」。預設追加，可依序加入多個檢查。取代會詢問是否覆蓋目前未保存的步驟。範例不猜測 APP 的 Start 按鈕；需要開始擷取時，請在檢查前加入該 APP 的點擊步驟。

| 範例 | 預設條件 |
| --- | --- |
| CH0 audio received | received > 0 |
| Running 狀態 | Running 或 Status: Running；排除 Not Running、Running=false |
| 1920 × 1080 | 接受 x、X、×、* 分隔及空白 |
| 約 60 FPS | 59～61，包含 59.94；可自行改範圍 |
| 整合檢查 | 依序檢查 Running、1920 × 1080、約 60 FPS |
| Video received frames | video 接收計數 > 0 |
| 預覽區有內容 | 框選區域亮度標準差 ≥ 8，或前後截圖平均 RGB 差異 ≥ 8；支援純黑／純白切換 |
| 預覽畫面有變化 | 至少相隔 500 ms 的截圖平均 RGB 差異 ≥ 2；取樣間隔輪替，允許純色畫面互換 |

文字範例載入後必須取 UIA 控制項或框選 OCR 區域；整合範例的三個步驟需分別設定。UIA 請選正確的即時狀態／實際訊號值，不要選設定欄位。控制項有 AutomationId 時優先使用該 Id，不同時限制會改變的 Name；沒有 Id 而 Name 會變動時，請自行設定 regex: 名稱條件，或使用 OCR。

影像範例不需要 OCR 引擎，但必須只框選預覽畫面內部，排除工具列、邊框、OSD 文字與其他 APP。門檻使用 0～255 量級，可在「預期值」調整。黑白互換可以透過前後截圖差異通過，固定純色則無法區分有效測試圖與無訊號黑場。畫面變化僅表示截圖改變，不測量實際 FPS；有限取樣仍可能錯過切換，錯誤提示／雜訊也可能產生差異，應配合 APP 的訊號狀態／接收計數交叉檢查。這些檢查不能證明擷取卡或外接螢幕的實際輸出。

影像檢查保存 step_N.png；變化檢查另存 step_N_before.png，log 顯示計算值與門檻。範例條件與影像演算法已用合成資料及獨立測試視窗檢查，目標 APP／硬體與 OCR 辨識準確度仍需自行試跑確認。
## 勾選建立與通用字串比對

按「建立測試項目…」，直接勾選 Running、解析度、FPS、畫面內容／變化、音訊／影像計數，或勾選「比對字串」並填入預期文字。比對方式可選等於（忽略大小寫與空白）、包含（忽略大小寫）、完全相同（區分大小寫與空白）或包含（區分大小寫）。字串按原文比對，不視為正規式；空白預期文字不能建立。

建立後選取該步驟，再「指一下文字／按鈕位置」指定 UIA 文字控制項，或「框選文字或預覽區域」使用 OCR。框選後可沿用已設定的比對條件。按單步試跑確認讀取值，再保存流程。插入或追加新檢查會保留原有目標與畫面上的測試結果。

## 框選文字與狀態判定

套件內附 Tesseract 5.4.0.20240606。工具旁 ocr/tessdata 包含英文、繁體中文語言資料及授權，預設自動使用 chi_tra+eng；繁體模型來自官方 tessdata_best，並補齊其直排模型依賴。

1. 選擇並開啟待測 APP，讓要檢查的文字顯示在視窗內。
2. 按「框選文字或預覽區域」，在截圖上拖曳圈出文字，按確認。不必先切到 OCR 類型。
3. 會開啟文字預覽視窗，自動顯示辨識結果。選中 Running／解析度／FPS 等既有文字步驟時，預設沿用原判定；選其他步驟時會新增文字檢查，不會取代啟動等動作。
4. 若要自訂，取消「沿用既定條件」，直接選文字等於、包含文字、數字大於或數字範圍，再填預期值。例如狀態必須為 Running，建議選「文字等於」並填 Running；包含文字也可能符合 Not Running，不適合拿來區分這兩個狀態。
5. 按「檢查這次辨識結果」看 PASS／FAIL，確認後按「保存這個文字檢查」。主畫面再單步試跑，最後保存流程。

文字等於會忽略英文大小寫與空白；Not Running 不會等於 Running。空白或辨識錯誤不會算 PASS。已以合成圖片驗證 Running、深底 Not Running 及繁體「執行中」；這不代表所有字體／大小／背景都能正確辨識。請看預覽文字是否正確，必要時重新框選、保留少量周圍空間或放大待測 APP 的文字。

目前畫面內容類型仍用框選範圍做影像內容／變化檢查，不會開啟文字判定視窗；位置點擊類型則保留框選中心作為點擊位置。

### 通用流程的 APP 重用與等待狀態

「重用已開啟的待測 APP；未開啟時才啟動」預設勾選，舊流程未指定此設定時也預設啟用。開啟步驟會重用同 EXE 已開啟視窗所屬的唯一程序；偵測到多份程序時會提示，請關閉多餘實例。取消勾選才每次啟動新程序。正式測試與試跑均採用目前 JSON 的此項設定。

「指一下文字／按鈕位置」依滑鼠實際指到的待測 APP 視窗保存標題與控制項；Start 按鈕應位於主視窗，影像檢查則選預覽視窗。有 AutomationId 的步驟若指定視窗失效或找不到控制項，會在同一待測程序的已開啟視窗中重新查找；只有唯一符合時才繼續，並更新步驟視窗設定，請保存流程。僅依位置的步驟須重新指選，OCR／影像區域不會套用這項自動重新定位。執行中會顯示步驟、等待秒數與目前讀取值；逾時條件在外部 UIA 呼叫返回後檢查，外部 provider 未返回時無法保證立即停止。

預覽建立等待：OCR／影像檢查會在該步驟的逾時內等待指定視窗出現（例如 Start 後延遲建立的預覽），等待時顯示目前狀態；視窗出現後先自動移回螢幕可用範圍，再擷取與判定。逾時仍找不到才 FAIL。

### 插入測試步驟

需要插入等待時，選取插入位置，按「在前插入…」或「在後插入…」，只勾選「等待時間（Delay）」並輸入秒數（0.1～600 秒），即可插入等待步驟，不需指定視窗、按鈕或框選區域。與其他項目一起勾選時，產生順序是點擊按鈕、等待、其餘檢查；可用上移／下移調整。

選取現有步驟，按「在前插入…」或「在後插入…」，使用勾選／文字介面建立新檢查。原有步驟的控制項名稱、AutomationId、待測視窗、框選區域及畫面上的 PASS／FAIL／讀取值會隨步驟保留，新步驟顯示未執行。插入模式不會取代流程，也不會自動加入開啟 APP／等待視窗。未選取列時插入至尾端；取消不改動流程。刪除只移除所選步驟；上移／下移時目標設定、測試結果與讀取值跟著步驟移動。追加檢查也會保留舊結果；執行完整流程時則仍會重新執行全部步驟。

## 將通用流程匯入開關機測試

匯入只記住 JSON 路徑；待測 APP 取自 JSON。擷取卡測試範例可在發行包的 examples/sample_capture_card_test.json 找到，請在編輯器開啟、選擇待測 EXE，再另存自己的 JSON。舊版快照設定需要重新匯入原始 JSON。

先按「試跑（不關機）」確認目前 JSON。正式測試輪數可設定為 1～999999 或不限。按開始後重新計算本次正式測試輪數，登入後自動續跑會沿用本次上限。達到上限時產出報告並停止；試跑不計入輪數。

主畫面顯示整份流程的最終結果，內部每一步的通過不會先算整份 PASS。每次執行保存至 boot_flow_results（流程、截圖與結果），總次數與 CSV 仍使用主要開關機測試的紀錄。通用流程 CSV 的 received_frames 為 0，詳細欄位記錄流程來源，這個 0 不代表音訊檢查結果。

若修改已匯入的原檔，下一輪會讀取保存後的內容。另存新檔時，請從主畫面匯入新檔。

### 檢查失敗時停止開機循環

「檢查失敗後，仍繼續下一輪」預設關閉。JSON 流程遇到 FAIL 時會停在失敗步驟並保存結果與原因。預設會寫入 FAILED 暫停自動續跑，Relay Agent 收到 FAIL 回報後會取消尚未送出的切電排程。勾選後，正式測試會記錄該輪 FAIL 並依設定續跑。手動停止、腳本停止和電源控制失敗仍會停止測試。

### RS485 Modbus RTU 定時斷電／復電

主畫面「RS485 電源設定…」提供兩段時間：「多久後斷電（程式計時）」與「斷電多久後復電（模組計時）」。例如 15 秒／20 秒表示檢查完成後程式倒數 15 秒，依負載接點送出一次閃閉或閃斷命令，模組切換接點並維持 20 秒，再自行切回。第一段倒數時待測電腦與程式必須保持執行，可按 STOP 取消；命令送出後由模組計時，STOP 不會撤銷已送出的動作。

此實作依使用者提供的模組指令圖片：設備位址預設 255、通道 1～4、鮑率 4800／9600／19200（預設 9600）、序列埠固定 8N1。實際模組須使用相同設定，COM port 從目前 Windows 串口下拉選單選擇；插拔設備後可按「重新整理」更新清單。功能預設停用，不會自動探測或修改設備位址、鮑率及光耦設定，也不會控制其他通道。

- 負載接點須符合實際接線：COM–NC（預設）使用閃閉（mode=4），平常釋放，暫時吸合斷電後釋放復電；COM–NO 使用閃斷（mode=2），平常須已吸合，暫時釋放斷電後吸合復電。選擇接點不會自動切換繼電器。TTL UART 接線為 TX→RXD、RX→TXD、GND→GND；UART 與 RS485 使用相同 Modbus RTU 命令。
- 設備位址採手冊的 1～255；不送位址 0 的設定／廣播指令。功能碼 0x10，通道起始寄存器為 0x0003 + (channel-1)*5，寫兩個寄存器，分別為模式與 0.1 秒單位的維持時間。維持時間為 0.1～6553.5 秒，斷電前等待為 1～3600 秒。
- 送出前記錄 TX（含 CRC），接收後核對設備位址、功能碼、寄存器、數量及 CRC，並記錄 RX；2 秒內沒有有效回覆或收到 exception 就記錄失敗，不重送，以免重設計時。無回覆時模組仍可能已動作。ACK 只證明模組接受命令，不證明 AC 已切斷或恢復。

**啟用時為直接斷電測試，不執行 Windows 正常關機。** 本指令的計時是切換後復原，沒有實作板端「先等正常關機完成再斷電」。模組必須獨立供電、接點與配線須適合負載；PC 須設定來電自動開機及登入後自動測試。未啟用時保留原本冷模式正常關機／外部恢復供電流程；暖重開機不送繼電器命令。

設定保存於 test_settings.ini 的 [Relay]：Enabled、Port、Baud、Address、Channel、NormallyClosed、DurationTicks、DelaySeconds。舊版 Mode 設定不再讀取，保存設定時會移除；NormallyClosed 缺省為 true，保留舊設定的 COM–NC 閃閉行為；false 使用 COM–NO 閃斷指令。視窗中的傳送預覽只計算封包，不開啟 COM port。主畫面試跑也不開啟 COM port、不送指令。CLI `--worker --describe-action` 可檢視已保存的冷模式封包與兩段時間，不執行電源動作；`--relay-self-test` 僅執行協定測試。

驗證邊界：軟體測試核對手冊的閃閉 2 秒完整封包（含 CRC）、回覆、exception／錯誤 CRC／錯誤通道拒絕及設定範圍。尚未連接實體 RS485 模組、量測接點或執行實際斷電循環。

### 確認 Modbus 通訊（不斷電）

在「RS485 電源設定…」選擇 COM port，設定鮑率與設備位址，按「測試通訊（不斷電）」。不必勾選啟用斷電循環，也不必先保存；測試使用畫面當下的設定，在背景執行，不切換接點、不關機、不自動重送。

測試只送功能碼 0x01，從位址 0 讀取 8 個繼電器狀態，沿用模組手冊封包；設備位址 255 時 TX 為 `FF 01 00 00 00 08 28 12`。收到符合設備位址、功能碼、資料數量及 CRC 的回覆才顯示「通訊成功」，並顯示四路模組回報的吸合／釋放狀態及 TX／RX。NC 接線下，吸合表示 NC 斷開，釋放表示 NC 導通；此為模組狀態，非實際電壓量測。

COM 開啟失敗、2 秒內無回覆、回覆不完整、CRC／位址／功能碼不符或 Modbus exception 都顯示失敗原因。僅開啟 COM 不算通訊成功。修改 COM port、鮑率或設備位址後須重新測試；成功代表當次請求收到有效回覆，不表示維持一條永久連線。測試結果顯示在設定視窗，不計入開機輪次的 PASS／FAIL。

`--relay-self-test` 含手冊讀取狀態封包與回覆解析測試；`--relay-ui-self-test` 使用不存在的 COM port 驗證視窗按鈕、錯誤顯示與設定變更提示，不存取實體模組。


COM port 清單在開啟設定視窗時自動更新，亦可按「重新整理」。只列出目前 Windows 的 COM 裝置名稱，不開啟串口。保留仍存在的原選擇；原串口已移除或沒有串口時，顯示提示並要求重新選擇，不自動改用其他設備。清單中出現不代表串口未被占用，或 Modbus 模組已回應，仍須按「測試通訊（不斷電）」確認。

## 主畫面流程監看

主畫面左側以步驟卡片呈現所選 JSON，另列準備測試與結果／電源動作階段。藍色為執行中、綠色為通過、紅色為失敗、黃色為停止；後續未執行的步驟保留灰色。點選卡片可查看完整設定與最近回報，執行中會自動捲動至目前步驟並顯示耗時。進度條僅計算 JSON 步驟的通過數，不包含準備及電源階段。

右側「流程與設定」集中匯入 JSON、編輯流程、冷／暖模式、輪數、失敗後繼續及自動啟動；「詳細紀錄」保留原始 log、紀錄資料夾與清除操作。開始後鎖定設定，仍可查看流程卡片及 log。

執行器會透過 FLOW_EVENT JSON 紀錄傳遞本次實際載入的流程、步驟開始、觀察值及結束結果，避免以人類可讀 log 推測步驟。新一輪重設步驟狀態；失敗、手動停止與程序異常退出時保留位置。重新開啟工具會預覽目前 JSON，歷史測試仍由 log／報告查閱，不會將歷史步驟狀態套在可能已修改的 JSON 上。電源階段的通過表示軟體動作已完成或命令已被接受，不代表已量測實體斷電或確認重開機完成。

維護驗證：`--flow-progress-self-test` 會在暫存資料夾執行延遲流程，驗證實際執行事件與 STOP 傳遞，不操作電源；`--ui-smoke-test` 包含步驟通過、失敗、停止及程序中斷狀態檢查。

## 工廠操作員與測試項目腳本

預設為操作員檢視：顯示測試名稱、版本、項目進度、目前項目、操作說明與失敗排查提示。右上角「工程檢視」可展開設定、詳細紀錄及底層步驟；這是顯示模式，沒有密碼或權限隔離。切換檢視不影響執行，執行中仍鎖定腳本與設定。

腳本建立方式：

1. 勾選「工程檢視」，按「編輯流程…」，開啟或建立通用步驟。
2. 按「測試項目與現場說明…」，填入測試名稱、版本，新增項目名稱、操作者說明、執行中提示與失敗排查提示。
3. 設定該項目的連續步驟範圍，按「套用步驟範圍」，再保存項目設定、保存 JSON。刪除項目不刪除底層步驟；未分配步驟的項目不顯示在操作員畫面。
4. 主畫面載入保存後的 JSON，試跑確認；交付工廠時提供同一份 JSON 與待測 APP 環境。

一個項目只有在所含全部步驟通過後才顯示通過。其中一步失敗，該項目顯示失敗；手動停止保留停點，未執行的項目維持未執行。重測會從整份流程開頭執行。操作說明不會自動新增人工確認或等待動作；需要等待時請明確加入原有等待／讀取條件步驟。

JSON 保持 schemaVersion=1，新增可選 name、version、testItems（id/name/instruction/runningText/failureHint）及每步的 testItemId。同一項目的步驟必須連續；編輯器會拒絕產生不連續分組的操作。舊腳本仍可載入，未分組步驟以既有名稱各自顯示；可逐步補上現場說明。工廠項目名稱與提示由建立者撰寫，不綁定特定 APP，也不改變 UIA／OCR／影像檢查的判定。

examples/sample_capture_card_test.json 取自已驗證的 test1.json，包含音訊與影像檢查。請先在工程編輯器開啟、指定實際 EXE 及控制項，另存後試跑；範本不含可直接使用的 EXE 路徑。音訊接收計數只證明 APP 回報收到資料，不代表已量測音量或實際喇叭輸出。

## 保存測試項目與現場說明

已有 JSON 檔案的流程，在「測試項目與現場說明」按保存時，會直接保存目前整份流程（含分類與步驟）回原檔。保存失敗會顯示原因；成功後關閉編輯視窗，首頁重新讀取所選 JSON。新流程尚無檔案時，仍須按「保存流程」選擇檔名，再從首頁載入。

## 掃描 APP 建立腳本

工程編輯器以「掃描 APP 建立腳本…」作為主要建立入口。先選待測 EXE、按 F6 開啟 APP，再選擇視窗掃描。掃描透過 Windows UI Automation 讀取控制項。「顯示進階設定」提供手動建立、範例、手動取點與 OCR。

掃描只讀取控制項，推薦可 Invoke 的按鈕操作，以及有唯一 AutomationId 的文字／輸入欄位檢查。名稱／ID 重複或不能可靠定位的控制項不允許勾選；自繪預覽及 UIA 未暴露的內容請改用手動／OCR。可選取目前停用的按鈕作為後續步驟，執行時仍須由 APP 啟用。多個同名視窗會要求先關閉多餘視窗。

勾選後可修改現場項目名稱、操作者說明與失敗排查；文字檢查必須自行填入「預期包含文字」，不會將掃描當下的值當作通過規格。按上移／下移決定執行順序。按鈕操作成功只代表 Invoke 成功，實際功能請另外加入文字／影像判定。掃描草稿支援按鈕操作和文字或數值判定。

按「加入腳本草稿」只追加到目前編輯器，不會執行、不會覆蓋現有步驟。每個候選會建立現場測試項目並綁好控制項。請確認順序、單步／完整試跑，最後保存 JSON。掃描上限 1500 個控制項；逾時、取消或不完整掃描不會產生候選草稿。掃描在背景執行；取消須等目前 UIA 呼叫返回。

## 掃描草稿直接設定數值 PASS 條件

選取文字控制項後，可直接在「PASS 判定方式」選文字包含／相等，或數值 >、≥、<、≤、等於、範圍。數值模式必須從「要判定的數值」選取明確欄位，再填門檻；範圍以最小值,最大值表示。下方顯示掃描當下的擷取值及判定預覽，執行時會重新讀取並最多等待 30 秒。

例如狀態文字同時包含解析度、Video received、Audio received、FPS，請選「CH0 Audio … received=」那一項、條件「數值大於」、門檻 0。產生的 JSON 保存帶行別與文字脈絡的擷取規則，不會直接取整段文字第一個數字。重複且無法唯一定位的數字欄位不列為選項；執行時擷取出現多筆亦拒絕判定，避免誤讀其他通道。進階編輯器的數字選取使用相同規則。

## 補充測試步驟

「在前補充／在後補充」與進階設定的「補充等待／畫面檢查」只提供等待時間、框選畫面有內容／有變化、框選 OCR 文字比對。按鈕與可讀 UIA 文字／數值判定請使用掃描 APP。補充步驟只追加，不取代原流程；畫面與 OCR 加入後須框選區域，等待不需目標。既有 JSON 的按鈕、Running、解析度、FPS 與接收計數等步驟仍可載入及執行。

## 掃描草稿插入位置

掃描視窗下方可選「插入到既有流程的位置」：任一步驟之前或流程最後。勾選的候選依掃描視窗的排序一起插入，不必先加到最後再逐個移動。若插入點位於同一現場測試項目的兩個步驟之間，選項會標示「併入原測試項目」；新步驟沿用該分組，以維持分組連續。原有步驟、目標設定與測試結果會保留。完成後仍須試跑並保存 JSON。

### 參考影片比較

在「前／後補充」勾選「參考影片：檢查畫面與顏色」，選擇本機同一支測試影片，再框選待測 APP 的完整影片內容。排除邊框、字幕浮層、控制列與黑邊，並維持長寬比。訊號來源以正常速度播放；本機只解碼參考檔，不必另開播放器。參考影片路徑寫入 JSON；相對路徑以 JSON 所在目錄解析。可在進階設定變更參考影片。

Windows Media Foundation 解碼本機短片（最多 120 秒，索引最長 45 秒，可隨時停止；格式支援取決於 Windows 解碼器）。解碼後才開始計算觀察逾時，預設 10 秒。正常畫面必須連續相符至少 3 秒且參考時間正常前進才 PASS；停格、靜態片段、循環交界、速度不同或無法對齊不會 PASS。取得相符畫面後若任何採樣不符，本次步驟即 FAIL。

先以不區分 RGB 通道排列的亮度結構尋找近似參考影格，再以 RGB 平均差與異常像素比例檢查顏色。固定門檻為平均差 ≤ 12（0–255）且差異 > 40 的像素比例 ≤ 8%。報告區分畫面相符、疑似紅藍顛倒、疑似局部異常、疑似偏色及無法對齊；疑似分類不是硬體故障原因的確診。

每次採樣保存 `step_N_video_M_actual.png`、`_reference.png`、`_difference.png` 與 JSON 指標；參考及差異圖為 160×90 的比較影格，actual 保存原始框選尺寸。這是預覽的抽樣比較（目標頻率可在「影像擷取設定」調整），不保證偵測細小瑕疵、單一壞影格或所有花屏，亦不能取代原始擷取資料逐影格驗證。背景模式需保持視窗開啟且未最小化；相容的前景桌面模式仍需視窗可見且能切至前景。先用已知正常硬體與選定短片試跑，確認條件適合後再交付現場。

### 背景擷取與採樣頻率

選取「畫面檢查／參考影片比較／OCR」步驟，按「影像擷取設定…」，可選擇背景視窗或前景桌面相容模式。背景模式使用 Windows Graphics Capture，無需取得焦點，允許其他視窗遮住；不可最小化、關閉或鎖定桌面。APP 必須繼續繪圖；若 APP 在背景自行停止呈現，擷取也無法取得新內容。受保護內容或不支援的系統可能拒絕擷取，此時會顯示錯誤，不會暗中切回桌面擷取。框選座標仍以視窗內容實體像素為準，視窗大小改變後應重新框選。

畫面與參考影片步驟可設定 1–120 FPS（預設 30）；這是目標頻率，非保證頻率。FPS 隨每個步驟存入 JSON。結果與 `step_N_sampling.json` 會記錄目標、實際成功採樣頻率及張數；影片還記錄每次採樣的時間與比較指標。為減少高頻採樣的磁碟負擔，比較圖片每秒保存一組，失敗樣本也保存；不再每次採樣都寫完整 PNG。實際頻率受視窗更新率、GPU、比較處理及存檔影響。OCR 仍逐次辨識，不使用此 FPS 設定。

背景適用於畫面、影片與 OCR 檢查；UIA 讀取與 Invoke 可否在背景操作取決於 APP。滑鼠座標點擊、鍵盤快捷鍵及輸入文字仍需前景。等待、文字與數值判定無需前景。

此變更提供背景擷取與可調採樣，尚未加入快速黑白閃爍的專用時序判定。重複黑畫面仍可能無法唯一定位影片時間，提高 FPS 也不保證捕獲每張瞬間白閃。

### 先擷取、再離線分析

畫面檢查及參考影片比較現在固定採兩階段流程。在「影像擷取設定」指定擷取秒數（0.1–600 秒，預設 10 秒）與目標 FPS；此秒數獨立於原有讀取逾時。擷取期間只取得視窗內容、裁切並製作最多 320×180 的 RGB32 比較影格，保留相對於擷取開始的毫秒時間戳；不搜尋參考影片、不做顏色判定、不寫入圖片，也不逐張更新 UI。記憶體暫存上限 256 MiB，達上限會中止並提示縮短時間或降低頻率。

擷取完成後，先將比較尺寸的影格與時間戳保存為 `step_N.gvfgcap`，才解碼參考影片並分析。這個檔案不是完整解析度的原始擷取影片；分析證據圖也使用已保存的比較尺寸。結果顯示實際採樣 FPS、張數、最大採樣間隔與離線分析耗時。時間戳為工具收到並複製影格的時間，非硬體擷取時間；採樣缺口不代表已確定來源掉幀。

選取相同類型的步驟，按「分析已擷取資料…」可選 `.gvfgcap`，以目前步驟的參考影片或門檻重新分析，不操作待測 APP。每次重新分析會在自己的結果目錄保存一份輸入資料及新報告。擷取或分析過程皆可停止。離線比對不會因前幾秒通過就忽略後面的異常。

此流程可減少比較運算對採樣的影響，仍不保證任何設備都達到目標 FPS；快速黑白閃爍的專用時序判定尚未加入，重複黑畫面的時間定位仍可能不明確。

### 任意起點與循環對齊

參考影片分析先從整段已擷取資料抽取分布於前後的影格，搜尋全片的起始偏移；再依各採樣時間追蹤預期位置，允許約 ±200 ms 的局部影格匹配。片尾回到片頭時，時間會累加影片長度，因此不要求與來源同時從頭播放。影片長度採解碼後的最後一張視訊影格結束時間，避免音訊尾端補齊影響循環長度。

報告新增起始偏移、影片長度、循環次數、實際畫面變動量；JSON 每張另存展開循環後的參考時間。此功能仍需內容可辨識、播放速度大致正常；持續不變、背景未更新、純黑或重複到無法區分的片段不能單靠預測時間證明播放正常。畫面變化不足會明確顯示，而非用倒退的片頭時間誤報。

### 擷取前啟用視窗（腳本動作）

「影像擷取設定」提供「前景相容：擷取前啟用預覽視窗（必要時才勾選）」，以每步驟的 `activateBeforeCapture` 寫入 JSON。勾選時，在真正開始擷取前啟用腳本指定的預覽視窗並確認前景成功，再使用已選的背景／桌面擷取方式；未勾選且使用背景模式時，不主動切換焦點。桌面擷取本身仍需要前景。

新步驟與缺少此欄位的舊腳本預設勾選，擷取前會啟用指定預覽視窗。可手動取消並保存 `activateBeforeCapture: false`，改成不主動切換焦點的背景擷取。編輯器與首頁共用同一個步驟執行邏輯，不再各自於流程開頭無條件切換主視窗。首頁會將 Windows 前景切換權限交給執行程序；權限或視窗啟用失敗會直接顯示「擷取尚未開始」的原因。重新分析已保存資料不啟用或操作待測視窗。


套件包含 `test_media/capture_card_test_1080p60.mp4`（1080p60、20 秒，含色條、灰階、細線、移動圖形、影格編號與立體聲同步標記）。`examples/sample_capture_card_test.json` 保留測試步驟，待測 EXE 預設指向 `../dut/gvfg_qt_preview.exe`；參考影片採相對於 JSON 的 `../test_media/capture_card_test_1080p60.mp4`。移動或另存腳本後請確認影片路徑。測試影片是高品質 H.264 / YUV420p / BT.709 素材，不是逐像素無損 RGB 參考。


交付資料夾中的 `dut` 是待測 APP 放置區：完整解壓工具，將 APP 連同 DLL／資源放入 `dut`，主 EXE 放在最上層，再載入範例腳本。預設目標是 `../dut/gvfg_qt_preview.exe`；不存在時自動採用 `dut` 內唯一的 EXE，多個時仍可載入，之後在編輯器指定主 EXE。之後整個資料夾可搬移。`package_release.bat` 會完整收進專案 `dut` 的內容，包括子資料夾、EXE、DLL 及資源；打包前請確認只放入要交付的待測 APP。


交付時請完整解壓最新 ZIP 至新資料夾，再啟動其中的 `bin/GVFG_BootCycleTest.exe` 並載入 `examples/sample_capture_card_test.json`；沿用舊解壓目錄時，本機設定可能仍指向先前選過的腳本。


首頁與編輯器使用相同的 FlowRunner。首頁透過獨立測試程序執行流程，程序異常退出時，主畫面會顯示退出碼並寫入詳細紀錄。試跑不執行繼電器切換或 Windows 電源動作。
